# ENDPOINTS.md — Flutter Feature → Backend Endpoint Mapping

This document maps every **frontend feature** (`flutter/lib/features/`) to the **backend endpoints** it consumes. The backend is organized by **domain** (Django apps), not by screen — this is intentional and follows Django best practice. Frontend "features" like `categories`, `products`, and `suppliers` are all one data domain (`apps/inventory`), while `admin`/`auth` are handled by `apps/users`, and `dashboard`/`reports` are aggregations served by existing apps. Use this table instead of restructuring the backend.

> **Phase 1b closed 2026-11-08 with owner-accepted QA limits; contract v0.2 provisional.** Requisition changes below are implemented/tested and core-live-QA verified; dev runs Phase 1b demo data since 2026-11-09 (not a deployment). Accepted gaps and evidence: [plan Handoff](planning/pos-evolution/phase-1b-plan.md#handoff--known-limits). Breaking backend/client/contract rollout and historical-amount rules: [CPMS contract](docs/integration/CPMS-CONTRACT.md#11-what-was-verified-and-where-the-code-lives).

| Item | Value |

| API prefix | `/api/v1/` |
| Auth scheme | JWT Bearer (`rest_framework_simplejwt`) |
| Header | `Authorization: Bearer <access_token>` |
| Health check | `GET /api/health/` (public, no auth) |

### API conventions (agreed — do not break)

| Topic | Convention |
| --- | --- |
| Pagination | **Enabled** — DRF `PageNumberPagination` with `PAGE_SIZE = 50` (`config/settings.py`). Every list response is an envelope: `{ "count", "next", "previous", "results" }`. Read `results`, and page with `?page=N`. |
| Error format | DRF default: `{"detail": "..."}` for auth/permission errors; `{"field": ["msg"]}` for validation errors. Frontend should read `detail` or the first field error. |
| Idempotency | `POST /api/v1/transactions/` and `POST /api/v1/held-carts/{id}/complete/` accept an optional `Idempotency-Key` header (≤64 chars). A key is scoped **per cashier AND per endpoint/cart**: the same key reused on a different endpoint, or on a different held cart, is a **409**, never a replay. Same key + same scope + same body → **200** with the **original** transaction and no new writes; same key + different body **or different scope** → **409** `IDEMPOTENCY_KEY_REUSED`; empty or >64 chars → **400** `INVALID_IDEMPOTENCY_KEY`. Generate one key per checkout attempt and reuse it for every retry of that attempt — a new key rings a second sale. **Browsers:** `Idempotency-Key` is a custom header, so it must be listed in `CORS_ALLOW_HEADERS` (`config/settings.py`) or the web preflight fails and the POST never leaves the browser. |
| 401 handling | Frontend retries once via `POST /auth/refresh/`; if that fails → logout to `/login`. |
| Null safety | Registration **requires** at least one role, but `role` in a user payload **can be `null`**: `createsuperuser`, an account created in the Django admin, or one whose group was removed has no group. `GET /users/` and `GET /auth/me/` both carry that null, so clients treat role as nullable — Flutter `User.role` is `Role?` and renders "No role" (Phase 3 Task 0). `roles[]` is the multi-role list and is **always present** (an empty list for a roleless account, which grants nothing). `id`, `username`, `email` and `full_name` are still always present, and a `role` that is present but **not** an object is still a contract break. |
| IDs | Integer PKs. Always serialize `id` in responses. |

### 3.2 `apps/users` — auth, admin, audit

| Method | Path | Purpose | Auth |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/login/` | Login (username or email + password) → JWT pair. **Lockout:** 5 failures for one `(identifier, client address)` pair inside 15 minutes → **429** `{"code": "LOGIN_LOCKED", "detail": "Too many failed sign-in attempts. Try again in N minutes.", "retry_after": <seconds>}` — answered **without checking the password**. A success clears the counter; the counter is kept in the cache (`apps/users/lockout.py`), so it expires by itself and is **per worker process** until production points `CACHES` at a shared backend. Every **checked** failure writes a `LOGIN_FAILED` audit row (a locked attempt is refused unread and writes none) (actor = the matched account, else `username_snapshot` = attempted identifier); the body for an unknown user and a wrong password is identical, and a disabled account's refusal counts as a failure | Public |
| POST | `/api/v1/auth/refresh/` | Refresh access token. Rotation is on: the response carries a **new** refresh token, and the token just used is blacklisted — **reusing a rotated refresh token → 401**. A **deactivated** account's refresh token → **401** (`no_active_account`) | Public (refresh token in body) |
| POST | `/api/v1/auth/register/` | Create account — the body names the account's roles with **`roles`** (`{"roles": ["pos", "sales"]}`, Phase 4 B3) **or** the legacy **`group_name`** (one existing Group). Exactly one of the two: sending both is **400 `ROLES_CONFLICT`**. A `group_name` must exist (the five POS roles in `apps/users/permissions.py` — `Admin`, `System Administrator`, `Store Manager`, `Stock Manager`, `Cashier` — or the `CPMS Service` group, which is **not** a POS role — it may only call `/api/v1/integration/cpms/` and is refused everywhere else, see §3.7). `roles` accepts the codes `admin`, `sales`, `inventory`, `pos`, `cpms` (case-insensitive), nonempty, no duplicates, and **`cpms` never beside a staff code**. `seed_demo` creates `System Administrator`, `Store Manager`, `Stock Manager`, `Cashier` and the `cpms_service` account, omitting `Admin`; guarantees every account has a non-null `role` | Admin **group** (`Admin` / `System Administrator`) or superuser |
| POST | `/api/v1/auth/logout/` | Logout. Optional body `{"refresh": "<token>"}`: when it parses **and** belongs to the caller, it is blacklisted (that token then fails `/auth/refresh/` with **401**). A garbage, expired, already-rotated or foreign token is ignored. **Always 204** — local sign-out never fails; a `LOGOUT` audit row is written either way | Authenticated |
| GET | `/api/v1/auth/me/` | Current user profile + roles | Authenticated |
| GET/POST/PUT/PATCH | `/api/v1/users/` | User CRUD (Store Manager + Admin). Query param: `?search=<term>` matches **username**, full name, or email. **No `DELETE`** — the route answers **405**; accounts are deactivated (`is_active: false`), never deleted (audit rows will `PROTECT` their user). `is_staff` is **read-only over the API**: it only grants Django `/admin` login, never application authority. **`PATCH`/`PUT` accept `roles: [codes]`** (optional, a full REPLACEMENT of the account's roles, same validation as `register`) beside the normal fields; it runs under the same last-admin lock as a deactivation. Non-admin callers get **403 `USER_ADMIN_FORBIDDEN`** on admin accounts (Admin / System Administrator groups or superuser, active or not) and on admin-group grants — through **either** role field; account creation stays Admin-only | Store Manager + Admin **groups** |
| GET | `/api/v1/users/stats/` | Account summary for dashboard cards: `{total, active, inactive, roles_assigned}` | Store Manager + Admin |
| POST | `/api/v1/users/{id}/assign_role/` | Assign roles — body: `{"roles": ["pos", "sales"]}` **or** legacy `{"group_name": "Cashier"}`; **replaces** the existing roles (not an addition). Returns `{detail, user}` with the updated user. Refused **400 `LAST_ADMIN`** when it would demote the last active admin; **400 `ROLES_CONFLICT`** when both fields are sent; **400 `{"roles": ["…"]}`** for an empty/unknown/duplicate list or `cpms` beside a staff code; **404** for an unknown legacy `group_name`; non-admin callers refused **403 `USER_ADMIN_FORBIDDEN`** on admin targets/grants (either field) | Store Manager + Admin **groups** |
| POST | `/api/v1/users/{id}/remove_role/` | Remove roles — body: `{"roles": ["pos"]}` (a code drops every group that code covers, so `admin` removes `Admin` or `System Administrator`) **or** legacy `{"group_name": "Cashier"}`. Returns `{detail, user}`. Refused **400 `LAST_ADMIN`** when it would demote the last active admin; **400 `ROLES_CONFLICT`** when both fields are sent; non-admin callers refused **403 `USER_ADMIN_FORBIDDEN`** on admin targets/grants (either field) | Store Manager + Admin **groups** |
| GET | `/api/v1/audit-logs/` | Audit trail — **append-only** and read-only over HTTP (no POST/PUT/PATCH/DELETE for any role, Django admin included). Row: `{id, user, user_email, username_snapshot, action_type, description, ip_address, timestamp}`; `user_email` is `null` when the actor is unknown. Action types: `LOGIN`, `LOGIN_FAILED`, `LOGOUT`, `CREATE`, `UPDATE`, `DELETE`, `USER_DEACTIVATE`, `ROLE_CHANGE`, `SALE`, `RETURN`, `RELEASE`, `CART_VOID`, `STOCK_ADJUST`, `RECEIPT`, `PAYMENT`, `REQ_APPROVE`, `REQ_REJECT`, `ALERT_RESOLVE`, `SHIFT_OPEN`, `SHIFT_CLOSE`. Every business event writes **exactly one** row inside the same transaction as the event (a refused or replayed event writes none); descriptions name the **document number** (`TRX-…`, `REQ-…`, cart/adjustment/alert id) and never a credential (no password, JWT or material-token UUID). `ip_address` comes from `REMOTE_ADDR` only. `username_snapshot` is the actor's name copied onto the row, so the trail still reads after the account is deactivated; rows cannot be edited or deleted (`PROTECT` on `user` as well) | Admin **group** |

**Authority is the Admin group, not `is_staff`** (decision 04): `is_staff` keeps one meaning — it may log into Django's `/admin` site. API authority comes from `Admin` / `System Administrator` group membership; superusers bypass role checks.

**Last-admin guard:** any `PUT`/`PATCH` setting `is_active: false`, any `PUT`/`PATCH` sending `roles` that drops admin authority, or any `assign_role` / `remove_role` (either field) that drops admin authority, is refused with `400 {"code": "LAST_ADMIN", "detail": "..."}` when that account is the last one that is active **and** is a superuser or a member of `Admin` / `System Administrator`. Deactivating a non-admin, or one of two admins, is allowed. Each guard decides under a row lock on the target plus every active admin, and the change and its audit row commit together.

**Roles — one or many (Phase 4 task B3, decision 18).** A user payload carries both the original single `role` and the new list `roles[]`, which share one object shape:

```json
"role":  {"id": 12, "name": "pos", "display_name": "Cashier", "permissions": []},
"roles": [{"id": 3, "name": "admin", "display_name": "Admin", "permissions": []},
          {"id": 12, "name": "pos", "display_name": "Cashier", "permissions": []}]
```

`role` is **unchanged** for released clients: the account's lowest-id group (superuser → a synthetic `{"id": 0, "name": "admin", "display_name": "Administrator"}`), `null` for a roleless account. `roles[]` lists every **recognised staff group** the account holds, deduplicated by code (Admin + System Administrator = one `admin`), in this stable order: **`admin`, `sales`, `inventory`, `pos`** (widest authority first, so `roles[0]` is the act-on area). Codes map to groups: `admin` → `Admin`/`System Administrator`, `sales` → `Store Manager`/`Sales`, `inventory` → `Stock Manager`, `pos` → `Cashier`. The `CPMS Service` group is deliberately **absent** from `roles[]` (it is not an area): such an account reads `roles: []` and `role` still names the group. Unknown groups made in the Django admin are likewise not listed. Writing a code grants its canonical group (`admin` → `Admin`, `sales` → `Store Manager`, `inventory` → `Stock Manager`, `pos` → `Cashier`), so a re-save of an account on `System Administrator` / `Sales` returns the canonical spelling — same authority, different group name. Roleless historical accounts stay readable (`roles: []`, `role: null`) and gain **no** access; nothing auto-grants.

Roles map to Django's built-in `Group`/`Permission` (see `apps/users/models.py` ERD mapping: USER → `apps_users.User`, ROLE → `auth.Group`).

One `CREATE` audit row per create, one `UPDATE` per **real** edit — a `PATCH` that changes nothing (`{}`, or only read-only fields such as `{"status": "ORDERED"}`) is **200** with the row unchanged and writes **no** audit row. | read: any authenticated · write: Stock Manager / Store Manager / Admin **Phase 5 B2 — money on the header (decision 18):** `discount_amount` (peso, `>= 0`, `<= gross`, else **400** `INVALID_PO`; editable only while DRAFT — a placed order answers `PO_LOCKED`), `vat_inclusive` (default **true**), and read-only `vat_rate` (the SNAPSHOT taken from `store-settings` when the order was created: the current rate, or **0** when the shop is not VAT registered) plus computed, read-only `gross_amount` (`SUM(ordered_qty × unit_cost)`), `net_amount` (`gross − discount`), `vatable_amount`, `vat_amount`, `total_amount`. **Tax-inclusive** (shelf/quoted prices carry VAT): `vatable = round(net ÷ 1.rate)`, `vat = net − vatable`, `total = net`. **Exclusive**: `vat = round(net × rate)`, `total = net + vat`. Every figure is rounded **2dp HALF_UP exactly once**. The header discount is what bills inherit; it is **not** in batch landed cost (`unit_cost ÷ conversion_factor` stays the per-base cost). A legacy order (pre-B2) reads `discount 0`, `vat_rate 0`, so its totals are unchanged. |

**Supplier cheque semantics (B1, decision 20 #3).** A supplier cheque lowers the bill balance **at issue** — the money is promised when the cheque changes hands, and the supplier's account is credited then. Its `status` therefore records only whether the bank honoured it: `ISSUED` on creation, then `CLEARED` (confirms money the bill already counted — nothing moves) or `BOUNCED` (the amount goes back on the bill). A decision is **once-only** and is taken under a row lock on the payment, then the bill, so two managers clicking together cannot restore a balance twice; the only other writer of those two rows (`record_supplier_payment`) locks the **bill** and never a payment, so there is no lock cycle. `save()` still refuses any change to a stored payment except exactly `{status, decided_by, decided_at, decision_reason}` while the stored status is `ISSUED` — an amount or method cannot be edited back. The `CREDIT` method choice exists for B3 and is refused (400 `INVALID_SUPPLIER_PAYMENT`) until a credit note can be named.

**Supplier payables semantics (B2, decision 18).** Every money figure on a bill is a SNAPSHOT and immutable at the model level (`save()` refuses a change to gross/discount/net/VAT/rate/total, the dates or the links; `delete()` is refused too), so a later `store-settings` change, a later supplier-terms edit or a later code path cannot rewrite what the shop owes — only `balance_amount` moves, and only through a payment. Bills are keyed **one-to-one to a receipt**, so re-processing a receipt creates no second bill. Receipts processed **before** this phase have none and never get one: **no retroactive debt is fabricated** for stock that was already settled outside the system (the upgrade boundary stated in inventory migration `0010`). Cashier and the CPMS service account are refused on every one of these endpoints (supplier money is neither till data nor part of the CPMS contract).

> ⚠ **Returns (decision 05, Phase 3).** `POST /api/v1/transactions/` with `source=RETURN` reverses a sale. Body: `{customer, source:'RETURN', original_transaction?, items[{variant_id, qty}], payment_method, reason}`. Every rule below is enforced **before the first write** — a refused return leaves no RETURN row, no restock, no payment, no ledger movement and no audit row.
>
> | Rule | Answer |
> | --- | --- |
> | Open shift | **400** `NO_OPEN_SHIFT` — a refund is money out of a drawer, and a drawer is a shift. The return is recorded against the caller's OPEN shift |
> | Reason | **400** `RETURN_REASON_REQUIRED` — non-empty, ≤255 chars, stored in `notes` |
> | Linked original, non-manager | **403** `UNLINKED_RETURN_FORBIDDEN` — a cashier returns against the receipt in hand; an unlinked return is a Store Manager / Admin correction (button on Sales Returns page, Phase 5 built) |
> | Original is a direct-till sale **not** rung by this cashier | **404** (hidden ≠ forbidden — the original is resolved through the caller's scoped queryset) |
> | Original is a return | **400** `RETURN_OF_RETURN` |
> | Original is a requisition release (`source=REQUISITION`) | **400** `RELEASE_NOT_RETURNABLE` |
> | Original is not `COMPLETED` | **400** `ORIGINAL_NOT_COMPLETED` |
> | Qty above what is left | **400** `RETURN_QTY_EXCEEDED` + `{variant_uom, sold, already_returned, requested}` (2-decimal strings) |
>
> **Qty cap:** per **selling unit** (`VariantUOM`), the cumulative returned qty across all returns linked to the original may not exceed the qty **sold on the original**. Read from `SalesItem` lines, so a pre-linkage sale that never recorded `SalesItemDeduction` rows is capped too; two lines of the same selling unit in one request count as one quantity. The original transaction row is `select_for_update`-locked for the whole block, so concurrent returns serialize and cannot together exceed the cap.
>
> **Money is DEBT FIRST:** if the original sale has a collectible ledger with `balance_due > 0` (OPEN / PARTIAL / OVERDUE), the ledger is locked and reduced by `min(return_value, balance_due)`, flipped to `PAID` at zero (else `PARTIAL`), and the reduction is written as a `CollectiblePayment` with `payment_method='RETURN_CREDIT'`, `official_receipt_no` = the **return's** `transaction_no`, `processed_by` = the cashier. Only the **excess** leaves the drawer: the return's `Payment` row is `-excess` in the requested method, and **no Payment row at all is written when the excess is 0**. So `compute_z_reading`'s `cash_refunds` is the cash excess only.
>
> **201 body** is the serialized RETURN transaction plus `refund_summary: {return_value, debt_reduced, cash_refund, refund_method, ledger_id, ledger_balance}` (2-decimal strings; `ledger_id`/`ledger_balance` are `null` when the sale had nothing owing). The `RETURN` audit row names the return number, the original number, the debt reduced and the cash refunded.

> ⚠ **Discount and VAT (decision 18, Phase 4 task B1).** The SERVER is the trust boundary: the cap, the approval and the VAT split are computed in Django, and the client's numbers are never input.
>
> **Request (checkout, and a held cart's `complete/`)**:
>
> ```json
> {
>   "customer": 3,
>   "source": "WALK_IN",
>   "items": [{"variant_id": 7, "qty": 2}],
>   "payments": [{"method": "CASH", "amount_tendered": "18.00"}],
>   "discount": {"kind": "PERCENT", "value": "10.00", "reason": "Loyal customer"},
>   "discount_approval": "<token from POST /discount-approvals/>"
> }
> ```
>
> `discount` is optional; when present, `kind` is `AMOUNT` (pesos) or `PERCENT`, `value` is a non-negative number, and `reason` is **required whenever the discount is above zero** (≤255 chars). `discount_approval` is only needed **above the cap** — omit it otherwise (a token is not burned by a sale that did not need it).
>
> **Response (201)** — the sale body carries the whole money story: `discount_amount`, `discount_reason`, `grand_total` (= **net**, what the customer pays), `change_given` (the change the cashier handed back, derived by the SERVER from the tenders it stored — read-only, `"0.00"` when the sale was paid exactly or is underpaid), `vatable_sales`, `vat_amount`, `vat_registered`, `vat_rate` (the rate stored on the row, `"12.00"`; `null` on rows that predate Phase 4).
>
> ```json
> {"grand_total": "18.00", "discount_amount": "2.00", "discount_reason": "Loyal customer",
>  "vatable_sales": "16.07", "vat_amount": "1.93", "vat_registered": true,
>  "change_given": "0.00"}
> ```
>
> **VAT is inclusive** (shelf prices already contain it): `vatable_sales = round(net / (1 + vat_rate/100))`, `vat_amount = net − vatable_sales`, where `net = gross − discount`. A non-VAT store answers `vatable_sales: "0.00"`, `vat_amount: "0.00"` and `vat_registered: false` — the receipt then says **Non-VAT**. `vat_registered` **and `vat_rate`** are stored **on the sale** (both read-only; `vat_rate` is the rate in force at that moment, `null` on rows written before Phase 4), so a reprinted receipt keeps claiming what it claimed when the money was taken, and a return books its VAT at **the rate the sale was rung at** — not at today's setting. A CPMS release (`source=REQUISITION`) gets the same breakdown, stores the same rate, and never a discount.
>
> **Utang and payments use the NET**: an underpaid sale posts `net − tendered` to the customer's ledger, so a discounted sale books the discounted amount.
>
> | Refusal | Answer |
> | --- | --- |
> | Discount above the sale total, a percentage over 100, a negative value, an unknown `kind` or a non-object | **400** `INVALID_DISCOUNT` |
> | A discount above zero with a blank (or >255-char) reason | **400** `DISCOUNT_REASON_REQUIRED` |
> | Above `discount_cap_percent` and **no** `discount_approval` sent | **400** `DISCOUNT_OVER_CAP` + `{cap_percent, requested_percent}` (2-decimal strings) — this is the code the till opens the approval dialog on |
> | Above the cap with a token that is forged, expired (>5 min), **already used**, minted for a smaller percent, or whose row disagrees with its signature | **400** `DISCOUNT_APPROVAL_INVALID` |
>
> A cashier cannot approve their own discount: `POST /discount-approvals/` checks the credentials against a **Store Manager / Admin** account, and a Cashier account is refused. Every refusal above writes nothing — no sale, no moved stock, no spent approval.
>
> **Returns of a discounted sale refund the NET share**, rounded ONCE per return: `refund = line gross × (sale net ÷ sale gross)`. Returning every line adds up to exactly what the sale was paid (never the gross, never a centavo more), and cumulative refunds can never exceed the sale's net. The return row carries the VAT back out of the reports the same way, at the **original sale's stored rate** (`vat_rate` on the response): changing the rate in Admin Settings between the sale and the refund cannot make the two disagree. A **legacy original with `vat_rate: null`** was rung when the shop booked no VAT (`vat_amount: "0.00"` on its receipt), so its refund is booked at `0.00` percent too and reports no VAT. An **unlinked** return (`original_transaction` omitted, Store Manager / Admin) has no original to read and uses the **current** settings — today's rate is the only one there is.

> ⚠ **Split tenders and cheques (decision 18, Phase 4 task B2).** One sale may take several tenders in `payments[]` — `CASH`, `CARD`, `GCASH`, `BANK_TRANSFER`, `CHEQUE` — in any combination, with or without a discount. The server never trusts a client total: it prices the lines, applies the discount, then reads what was tendered.
>
> **A cheque is not money yet.** A `CHEQUE` tender carries its number, bank and cheque date, is stored `PENDING`, and does **not** count as paid. The shortfall (`grand_total − every tender that is not a pending cheque`) posts to the customer's utang ledger through the ordinary underpayment path, and the cheque is linked to that ledger (`ledger` on the row). A Store Manager or Admin decides it exactly once, at `/cheques/{id}/clear/` or `/bounce/`.

> **Delivery charge (decision 18, Phase 5 task B3).** `POST /api/v1/transactions/` and `POST /api/v1/held-carts/{id}/complete/` accept an optional `delivery` object — `{address, contact_name, contact_phone, scheduled_date: "YYYY-MM-DD", fee}` — and so does `POST /api/v1/sales-orders/` (write-only, read back on `/deliveries/`). All four fields except `fee` are **required**; `fee` defaults to `0.00` and must be a non-negative amount of whole centavos (`10.005` is refused, not rounded). Anything unusable → **400** `{"code": "INVALID_DELIVERY", "detail": …}` with **no sale, no moved stock and no delivery row**.
>
> The fee is a **"Delivery charge"** on the receipt: **VAT-INCLUSIVE**, priced from **no stock**, and it joins `grand_total` **after** the discount. `discount_amount` and its percent cap stay on the GOODS gross, so a percentage never eats the delivery charge; `grand_total = goods net + fee`; `vatable_sales`/`vat_amount` split **that** `grand_total`; change, the utang shortfall and the cheque-vs-owed check all measure the new `grand_total` (so a walk-in must pay the charge too — `WALK_IN_CANNOT_OWE` still applies). The charge is stored on the sale as **read-only** `delivery_fee` as well as on the `Delivery` row, and the Z-reading's `gross_sales` includes it (the drawer holds it).
>
> **A return refunds the GOODS only.** `_return_net_share` prices the refund against `grand_total − delivery_fee`, so a full return of a delivered sale gives back the goods net and **not** the charge — the trip was still made. Refunding the charge itself is **out of scope** for this phase. A **sales order** carries no money total on the wire, so its fee lives on the `Delivery` row alone until the **first fulfilment** (Phase 7 B4) re-links that slip to the sale it bills and carries the fee into that sale's `grand_total` — **once**.
>
> **Sales-order lifecycle (Phase 7, decision 19).** An order is a DOCUMENT: nothing moves in the stock ledger and no money is taken until it is fulfilled at the till. Status is server-owned — `CONFIRMED → PARTIAL → COMPLETED` as lines are rung, `CONFIRMED → CANCELLED` (or `PARTIAL → COMPLETED`, remainder written off) through `cancel/`; legacy `PROCESSING`/`READY` rows **read as `CONFIRMED`** on the wire (`status` is the effective status) and no path writes them again. A manager edits or cancels with a **reason** (audited `SALES_ORDER`); a cashier fulfils. **No stock is reserved** anywhere: `available_qty` is a live hint, and the shelf is checked (and taken) only when a fulfilment is rung. **The delivery fee is charged exactly once**, on the first fulfilment; later fulfilments carry none and refuse a `delivery` object. **A create-time approval token is spent by that order; an edit re-pricing lines above the cap needs a FRESH token.** A **return** of a fulfilment sale follows the ordinary return rules — refunded at the price the line SOLD at — and never reopens the order or moves `fulfilled_qty`.
>
> Delivery creation and status moves are audited as `DELIVERY` rows; the slip's statuses are `SCHEDULED → OUT_FOR_DELIVERY → DELIVERED`, or `FAILED` (with reason) from either live state — forward-only, terminal states final.
>
> ```json
> {"customer": 3, "source": "WALK_IN",
>  "items": [{"variant_id": 7, "qty": 2}],
>  "payments": [
>    {"method": "CASH", "amount_tendered": "5.00"},
>    {"method": "GCASH", "amount_tendered": "5.00", "reference_no": "G-77"},
>    {"method": "CHEQUE", "amount_tendered": "8.00",
>     "cheque_number": "CHQ-1001", "bank": "BDO", "cheque_date": "2026-11-20"}],
>  "discount": {"kind": "PERCENT", "value": "10", "reason": "Loyal customer"}}
> ```
>
> With a 20.00 gross and a 10 percent discount the net is 18.00: cash 5.00 and GCash 5.00 are paid, so 8.00 lands on the customer's ledger with the cheque holding it open. The **Z-reading counts the 10.00**, not the cheque — it is not in the drawer.
>
> **Change comes from the DRAWER only.** A cheque may never be tendered above what the sale still owes, so the till cannot hand back cash for funds the shop has not received. Every tender that is not a cheque is `CLEARED` on creation.
>
> **Change is recorded on the sale (`change_given`).** Money in hand is every tender that is not a pending cheque; anything above `grand_total` is change the drawer paid out, so the server stores `change_given = max(0, money in hand − grand_total)` and the Z-reading subtracts it from the cash tendered (a 225.00 sale paid Cash 230.00 + GCash 10.00 is 15.00 change and 215.00 of cash takings). Because only the drawer can pay change back, a tender set whose change exceeds the **cash** taken (e.g. GCash 240.00 on a 225.00 sale) is refused — the sale rolls back wholesale and the cashier lowers the card/GCash amount. The shortfall/utang arithmetic is unchanged.
>
> | Refusal | Answer |
> | --- | --- |
> | A cheque against the walk-in record | **400** `CHEQUE_NEEDS_CUSTOMER` — nobody would owe the pending amount, so name the customer |
> | A cheque missing its number, bank or date (or a date that is not `YYYY-MM-DD`) | **400** `CHEQUE_DETAILS_REQUIRED` + `missing: ["bank"]` |
> | Cheques worth more than the sale still owes (e.g. cash already covers it) | **400** `CHEQUE_EXCEEDS_BALANCE` + `{cheque_total: "5.00", owed: "0.00"}` |
> | Non-cheque tenders whose change is more than the CASH taken (e.g. GCash 240.00 on a 225.00 sale, or cash 5.00 + GCash 240.00) | **400** `PAYMENT_EXCEEDS_TOTAL` + `{change_given: "15.00", cash_tendered: "0.00"}` — change is paid from the drawer, so lower the card/GCash amount |
> | A **refund** (`source=RETURN`) with `payment_method: "CHEQUE"` | **400** `INVALID_RETURN` — a refund leaves the drawer; a cheque is decided with `clear/` |
>
> A refused cheque writes nothing: no sale, no moved stock, no ledger, no payment row.

> **Review validation and conflicts:** false lines require trimmed nonblank reasons (≤255 chars); true lines require blank reasons. Whole Decline requires a nonblank reason (≤255). Unknown action keys, including quantity/price/status edits, are rejected. Payload errors are field-shaped **400**; stored-line-set refusals use **400 `INVALID_REQUEST_REVIEW`**. Repeated/opposite/stale decisions after review or close → **409 `REQUEST_ALREADY_REVIEWED`**, no writes/audit. Unknown id → **404**. Reload authoritative detail on 409/uncertain outcome; do not blindly retry a decision. CPMS cannot call these staff actions (**403 `CPMS_SCOPE`**).
>
> **Budget semantics:** `available` is true/false/null store intent, not the till's live `availability` enum. `expected_amount` is a nullable 2dp **budget**, never debt or a quote: known persisted released total + current prices × outstanding true-line quantities, outstanding component rounded once with `ROUND_HALF_UP`. Closed-after-accept keeps abandoned shortfall in that budget; before-review/declined/unreviewed legacy/historical unknown stays null, even after more releases. Payments change debt, not budget. Full rules/example and migration safety: [contract §6.1](docs/integration/CPMS-CONTRACT.md#61-expected-amount-is-a-budget-not-debt).
>
> ⚠ **Release what is there (decision 05).** One call FIFO-deducts stock and writes ONE `SalesTransaction` (`source=REQUISITION`) with ONE official receipt and ONE `CollectibleLedger` row tagged with the request's **project** (decision 03) — so receivables total per project as well as per contractor, and `GET /ledgers/` carries `project_name` on every row (`null` for a counter sale). Only eligible lines with stock are written; false lines never consume stock. A short, out-of-stock or archived eligible line keeps the request **`PARTIAL`** and **the same token stays valid** for another visit. When every Available line is out the request becomes **`RELEASED`** and the token is spent, even if false lines retain positive numeric outstanding. Verify shows false lines with reason, `availability: UNAVAILABLE` and `releasable: "0.00"`. Lines are counted in their own **selling unit** and stock leaves by that unit's conversion factor (the till's rule); whole-count units release whole numbers, measured units to 2 decimals, always rounded down.
>
> ⚠ **Release needs the caller's OPEN shift** (decision 03): with none → **400** `{"code": "NO_OPEN_SHIFT", "detail": "…"}`, and nothing is written (token unused, stock unchanged, no sale, no ledger, no `RELEASE` audit row). A successful release attaches that shift to its `SalesTransaction`, so it counts in the Z-reading's `transaction_count` / `gross_sales` while leaving `expected_drawer` untouched — a release books a collectible, never cash.
>
> ⚠ **Scanner refusals** — all **400**, all writing nothing. Release with no eligible quantity on the shelf → `{"code": "NOTHING_TO_RELEASE", "detail": "…"}`; token stays usable after restock. Verify can return a plan with zero releasable quantities rather than this refusal. Both endpoints require `ACCEPTED`/`PARTIAL`; other named statuses → `{"code": "REQUISITION_WAITING" | "REQUISITION_DECLINED" | "REQUISITION_CLOSED" | "REQUISITION_RELEASED" | "REQUISITION_CANCELLED", "detail": "…"}`, checked **before** generic used-token refusal so a declined token explains the store decision. Used tokens on otherwise releasable requests and unknown UUIDs keep plain `{detail}`; malformed UUID payloads are field-shaped validation errors. Verify is advisory; Release repeats checks under token-then-request locks shared with review/close.
>
> ⚠ **Tokens are bearer credentials.** Whoever holds a `MaterialToken` UUID can take goods out on the project's credit, so `GET /tokens/` is manager/admin-only and `GET /requisitions/` shows `token` to a Store Manager / Admin only. A cashier releases with the UUID the project brings to the counter; reading it is not part of their role. The CPMS service account is fenced out of this whole app (`403 CPMS_SCOPE`).
