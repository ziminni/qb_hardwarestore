## 1. Architecture

Two processes, one database. A Flutter client talks to a Django REST API; the API owns **all** business logic and persists to PostgreSQL 15. Data screens read API responses; store contact constants and access-scope banners remain static (VAT and discount settings are now API-backed) — zero `*MockData`/`Simulator` files remain in `lib/` (all deleted; only comments reference the mock era, and Phase 1d removed the last fake one). The server is the trust boundary: Phase 1 (server price/UOM authority, `INVALID_SALE` validation, credit-limit block, locked `DocumentCounter`, `Idempotency-Key` de-dupe) · Phase 2 (Admin-group authority + `LAST_ADMIN`, cashier-own scoping, token secrecy) · Phase 3 (open-shift gate, debt-first returns with `RETURN_CREDIT`) · Phase 4 (catalog persistence, two-step receive+process, append-only records) · Phase 5 (`IsUserManagerRole`: Store Manager user-write with `USER_ADMIN_FORBIDDEN` guardrails, manager-only unlinked returns) · Phase 6 (unique `barcode_qr` per selling unit — factory EAN/UPC GS1-checked or auto-derived `QB` code; `?barcode=` lookup; till scans resolve the unit with server fallback; 50×30 mm Code 128 stickers from Products + Receiving; per-unit code edit) · POS evolution Phase 1 (`CPMS Service` role behind `CpmsFencedJWTAuthentication`: 403 `CPMS_SCOPE` outside `/api/v1/integration/cpms/`; CPMS pushes approved requests, imported contents stay read-only). Phase 1b adds the store's separate Accept/Decline decision before release; only accepted lines can leave, `PARTIAL` keeps the token alive, and utang carries the project. Phase 1d moves what a whole unit means onto the server (`UnitOfMeasure.is_whole`), seeds the twelve standard units in every database, lets a store remove an unused selling unit, and refuses a fractional quantity on a whole-count unit on every path that carries one. POS evolution Phase 4 (front counter, decision 18): shelf prices are VAT-inclusive and the server splits `vatable_sales`/`vat_amount` from the net, storing a per-sale `vat_rate` (returns use the sale's rate; legacy null = 0%); Admin-only `StoreSettings` holds VAT on/rate and the discount cap; a cashier discount needs a reason and stays within the Admin cap unless a Store Manager/Admin approves on the spot through a one-time 5-minute signed token (`POST /discount-approvals/`; five failures lock the pair, 429 `DISCOUNT_APPROVAL_LOCKED`, password never stored); split tenders record a server `change_given` from cash only, and a non-cash overpay is refused 400 `PAYMENT_EXCEEDS_TOTAL`; customer cheques are `PENDING`/`CLEARED`/`BOUNCED` and never reduce debt until a manager clears them; accounts carry several roles (`roles[]`) with an area picker and header switcher; shared `DataPanel` pages at 25 rows; Products exports a barcode PDF/CSV masterlist whose CSV prefixes formula-leading cells with `'`. **Phase 6 (cleanup, decision 22) changes no entity, route or screen — it makes existing writes obey their own contract.** A sales order is **create-only** until Phase 7: `SalesOrderViewSet.http_method_names` drops `put`/`patch`/`delete`, so every role including Admin gets **405** and an order with a `Delivery` (a `PROTECT`ed FK) can never answer a `ProtectedError` **500**; the order, its lines, its optional delivery and its one `CREATE` audit row commit or roll back together. A quotation's `status` is read-only, rewriting or erasing one is Store Manager/Admin only, and those writes carry their `UPDATE`/`DELETE` audit row in the same transaction; a nested `items` write on update is refused **400** instead of tripping DRF's model-serializer `AssertionError`. Both document types refuse a line naming an archived variant or an archived product's variant with **400 `INACTIVE_SELLING_UNIT`** before the first write (no few rows, no audit row, and no counter increment). Quotation/order/delivery/requisition numbers now come from the same `DocumentCounter` row lock the till already used, so two concurrent creates get distinct numbers instead of a duplicate-key 500. In Flutter, the till's low-stock badge reads the product's own server `minStockThreshold` as a threshold (the flag itself is computed client-side, not sent by the API), the receipt prints the server's `change_given`, the order form and pay dialog share one money validator, long money errors wrap instead of clipping, a null VAT rate reads “Not recorded” (never an invented 0 %), a legacy product with no location id can finally take one, and a double-tapped “add location” no longer claims success. **Phase 5 (back office, decision 18) adds four entities and one additive column set:** a PO line names its `variant_uom` so packages are ordered and received in that unit while stock enters in base units (`qty × factor`, landed cost per base = unit cost ÷ factor); processing a goods receipt writes one immutable `SupplierBill` (received value less its discount share, VAT snapshot, receipt date + supplier `terms_days`) with locked, audited partial `SupplierPayment`s (Store Manager/Admin pay, Stock Manager reads); a `Delivery` slip (address, contact, scheduled date, fee) hangs off a sale **or** a sales order and moves forward only (SCHEDULED → OUT_FOR_DELIVERY → DELIVERED / FAILED + reason); `StorageLocation` (seeded Store, Bodega) is an Admin-managed label behind `Product.stored_at`. ### Phase 1b — project request lifecycle

- Import → `WAITING` (line `available=null`). CPMS approval is not store acceptance. Store Manager/Admin answers once: `ACCEPTED` with every line explicitly true/false and at least one true, or whole `DECLINED` with a reason. Strict JSON booleans only; false requires a trimmed reason, true requires no reason; unexpected fields and quantity/price/status edits are refused. Accept reserves no stock and books no money.
- `available` is three-valued **store intent**, not live shelf `availability`. False lines never consume stock or hold completion open. Only `ACCEPTED`/`PARTIAL` releases; all eligible lines finished → `RELEASED`, even with truthful outstanding quantities on false lines. `WAITING`/`DECLINED` scans return typed `REQUISITION_<STATUS>` before generic token-used checks.
- Accept/Decline/Close/Release share token→request row-lock order and re-read fresh state. `PARTIAL` keeps the token live; `RELEASED`/`DECLINED`/`CLOSED` spend it. CPMS may close `WAITING`/`ACCEPTED`/`PARTIAL`; closing terminal states is a no-op (legacy `CANCELLED` remains 409).
- Nullable persisted `released_amount` accumulates known **persisted sale totals** only. `expected_amount` = known released total + sum(current selling price × true-line outstanding), outstanding sum rounded once `ROUND_HALF_UP`. It is a live budget, independent of debt/payments, not a quote. Unknown historical totals stay null across future releases; WAITING/DECLINED/unreviewed legacy rows have no budget. CLOSED after acceptance retains abandoned accepted shortfall; CLOSED before review stays null. CPMS read-back adds decisions/reasons/budget, not unit prices, stock or token.
- Two new URLs, one shared queue body/VM: `/admin/project-requests` (sidebar **7**) and `/sales/project-requests` (**8**), appended without renumbering; `salesTwinOf` keeps managers in their shell. CPMS approver stays separate from store reviewer/audit. Old approvals URLs and foreman stay retired.
- Queue is oldest-first, selected-status page walk with a fail-loud **40 × 50 = 2000-row** bound; not a silent completeness claim. Badge uses server `Paged.total` for all WAITING, independent of search/status selection; failed reads are not zero. Unknown write outcomes/unreadable successes and 409 reload authoritative detail before retry; failed refresh blocks actions. Latest-generation reads and dispose-safe notifications guard async state; saved-but-stale copy distinguishes success from refresh failure.

### Phase 1d — the unit decides, not the client

- `UnitOfMeasure.is_whole` (boolean, default false) is the one source of truth for "counted in ones". [Migration 0008](../backend_django/apps/inventory/migrations/0008_uom_is_whole.py) adds the column and seeds **12 standard units** in every database (`PC`, `BAG`, `BOX`, `PACK`, `ROLL`, `SHEET` whole; `KG`, `G`, `M`, `CM`, `L`, `ML` measured). Lookups are case-insensitive because codes are unique only case-sensitively, an existing row is flagged rather than recased, and `RL` is accepted as the Roll row so no second Roll is created. The reverse direction deliberately deletes nothing: selling units and past lines may point at those rows.
- The Flutter client no longer carries a code list. `lib/core/units/whole_units.dart` is deleted; the till reads `uom_is_whole` off the selling unit, and the details dialog prints `Whole` or `Measured` in words, not colour alone.
- One refusal, one code: `common/exceptions.py` `WholeUnitQuantity` (400 `WHOLE_UNIT_QUANTITY`, detail naming the line, product and unit) with the shared `refuse_fractional_whole_unit` helper. The rule lives in `common/` because it spans both directions of the app dependency graph — the POS validator, the quotation/sales-order/purchase-order serializers, the goods-receipt view, the stock-adjustment serializer and the CPMS import all ask it, and none of them may import another app's API module to do so. Every raise site checks **before the first write**, so the 400 also means nothing changed. Paths refusing: sale, held-cart complete, return, release, quotation, sales order, purchase order, goods receipt, stock adjustment, CPMS import.
- `unit_is_whole` / `uom_is_whole` / `in_use` are read-only on the serializers. `in_use` is one query via `annotate_unit_in_use`, so a list of products costs no N+1.
- `DELETE /api/v1/variant-uoms/{id}/` removes an **unused** extra selling unit. 400 `BASE_UNIT_REQUIRED` for the factor-1 unit (removing it would leave every quantity counted in a unit the product no longer has); 400 `SELLING_UNIT_IN_USE` when any of the five PROTECT tables references it (sale line, held cart, project request, quotation, sales order); 404 for a bad id and for a second delete of the same row, never a 500. Price and code stay editable either way; the audit row is written inside the same transaction, so a success is 204 plus one `DELETE` row and a refusal writes nothing.
- Removal and the writers share a lock: `apps/inventory/services.py` `lock_selling_units` / `lock_selling_unit_lines` take `select_for_update()` in **sorted PK order** over the units a write is about to reference. Removal takes the same row lock, so the read-then-write window is closed in both directions and two writers queue in one order instead of deadlocking. A unit that vanished between read and lock becomes 400 `SELLING_UNIT_IN_USE` naming the line, not a foreign-key 500.
- `seed_demo` demonstrates the contrast on one product: Tile Adhesive sells as `KG` (measured, so 2.5 kg is legal) and as `BAG` = 25 kg through a real purchase order plus receiving, so the packaged unit is stock-backed rather than typed in by hand.

### Phase 4 — front counter

- **Settings.** `StoreSettings` is a database-enforced singleton (`pk=1` check constraint): `vat_registered` (default true), `vat_rate` (12.00), `discount_cap_percent` (10.00). `GET /api/v1/store-settings/` for any signed-in user, `PATCH` Admin only, audited. The Admin Settings page edits these through the app-scoped `StoreSettingsViewmodel`; store name/email/phone remain inline constants.
- **VAT.** Shelf prices include VAT, so `vat_split` works backwards from the net: `vatable_sales = net / (1 + rate/100)`, `vat_amount = net − vatable_sales`, `ROUND_HALF_UP` once. Non-VAT stores get 0/0 and a flag. Each sale stores its own `vat_rate` (pos 0013), so a linked return refunds under the rate the sale was made at; legacy rows hold null and read as 0%, and an unlinked return has no original to read and uses today's settings.
- **Discount.** Optional `discount {kind: AMOUNT|PERCENT, value, reason}` on checkout and held-cart complete; percent is of gross, reason required above zero, never above gross. Above the cap the sale needs a `discount_approval` token from `POST /api/v1/discount-approvals/`: Store Manager/Admin credentials checked server-side, never stored; the token is a signature over a `DiscountApproval` row, bound to the percent, valid 5 minutes and spent under a row lock by one sale. A cashier cannot approve themselves. The endpoint shares the login lockout (`apps.users.lockout`): five failures per (username, address) answer 429 `DISCOUNT_APPROVAL_LOCKED`, each failure audited without the password. Returns refund each line's net share (line gross × sale net ÷ sale gross). Reports show Discounts and VAT again.
- **Split tenders and change.** `payments[]` may mix cash, GCash and cheque. The server computes `change_given` (pos 0014): money in hand above the net, capped at cash tendered; a non-cash overpay is refused 400 `PAYMENT_EXCEEDS_TOTAL`. The Z-reading subtracts change from `cash_sales`, which fixes a pre-existing drawer overstatement QA found on any cash overpay. The receipt prints the server's change.
- **Cheques.** No new model: a cheque is a `Payment` row with `method=CHEQUE`, `cheque_number`/`bank`/`cheque_date` and `status` `PENDING`/`CLEARED`/`BOUNCED` (other methods `CLEARED`; pos 0012 backfills old rows). A cheque needs a named customer (`CHEQUE_NEEDS_CUSTOMER`). A pending cheque is not paid: its amount posts to the customer's utang ledger, linked by `Payment.ledger`, and only `POST /cheques/{id}/clear/` applies a ledger payment; `bounce/` (reason) leaves it owed. Store Manager/Admin only, once-only 409 `CHEQUE_ALREADY_DECIDED`, locked and audited. Utang payments offer the same cheque option (collectibles 0003 shares the method choice). Refunds never pay out by cheque.
- **Several roles.** User serializer returns `roles[]` (recognized staff areas, deduplicated in stable order; CPMS/ad-hoc groups excluded) beside legacy `role`; admin writes send `roles[]` as a full replacement, with `USER_ADMIN_FORBIDDEN`/`LAST_ADMIN` applying to every role added or removed and `CPMS Service` never combinable with staff roles. Client: one area signs straight in; several land on `/select-area` (`AreaPickerPage`, the 41st route); the header `AreaSwitcherMenu` changes area; `redirectFor` honours a stored choice only while the server still assigns it (`active_area_store.dart`, per device).
- **Pager and labels.** `DataPanel` pages client-side at 25 rows ("1 to 25 of N", hidden at 25 or fewer, `paginate: false` opt-out, reset on filter). Products gains a **Barcode list** export (`features/labels/barcode_list_{document,csv,dialog}.dart`): A4 PDF with EAN only on a valid check digit, else Code 128; CSV with BOM and a `'` prefix on cells starting `=`, `+`, `-`, `@`, tab or CR.

### Phase 5 — back office: packages, payables, delivery, bodega (owner-closed)

**Order by package (B1/F1, inventory 0009).** `POItem.variant_uom` names the selling unit the line is written in; the migration backfills every existing line to its variant's base unit, so an old line keeps meaning factor 1. `ordered_qty`/`unit_cost` are in **that** unit and the whole-unit rule is that unit's. Receiving counts in the line's unit; the batch is written `qty = received × factor` with landed cost per base unit `unit_cost ÷ factor`. A conversion not exactly representable in two-decimal base stock is refused 400 `RECEIPT_QUANTITY_UNREPRESENTABLE` before any write, and a referenced unit is frozen (identity + factor) with the same sorted-PK deletion locks as Phase 1d, so changing a factor never re-measures existing orders. The receiving page shows the line's unit and the "10 BAG = 250 kg" helper.

**Supplier payables (B2).** Processing a goods receipt writes exactly **one** `SupplierBill` inside the same transaction, from the receipt's own package qty × package cost, less that receipt's cumulative cent-exact share of the PO discount, with the PO's VAT snapshot and `due_date = receipt date + Supplier.terms_days` (default 0 = on receipt). A receipt with zero gross value makes no bill, and **pre-B2 receipts get no retroactive bill**. Bills are immutable: no POST/PATCH/DELETE for any role, Admin included. `SupplierPayment` (cash / cheque / bank transfer, optional reference, cheque no./bank/date, partial allowed, never above the balance) moves the bill balance under a row lock and is audited in the same transaction; refusals are 400 `OVERPAYMENT` and `BILL_PAID`. `GET /suppliers/payables/` returns per-supplier original/paid/balance/overdue. PO header gained `discount_amount` and `vat_inclusive` (default true, rate from store settings) for its totals — the discount and VAT live on the header and reach the **bill**, never the batch landed cost.

**Delivery (B3, pos 0015, users 0005).** A `Delivery` hangs off exactly one sale **or** one sales order (model check constraint) and carries address, contact name/phone, scheduled date, fee and status. It is created inside the sale's / order's own atomic block, so no standalone `POST /deliveries/` exists (405 for every role including Admin) and a refused sale leaves no slip. Transitions only move forward under a row lock with a re-read: `start` (SCHEDULED → OUT_FOR_DELIVERY), `deliver` (→ DELIVERED, terminal), `fail` (→ FAILED, required reason); a stale move is 409, and each move writes one audit row.

**Financial truths (verified in `process_sale` / `process_return`).** The delivery charge is charged **on top of the goods net and is never discounted** — `gross` and the discount cap are computed from the lines only, `grand_total = goods_net + delivery_fee`. The VAT split is taken from that grand total, so the receipt adds up to what the customer actually pays; the fee is stored on the sale (`delivery_fee`) as well as on the slip, because the receipt, Z-reading and change arithmetic read the sale. **Owner-confirmed 2026-11-12:** the discount cap and the return's net-refund share exclude the delivery fee (`sale_net = grand_total − delivery_fee`), a delivery fee is not refunded, a zero fee is allowed, and a sales-order delivery fee lives only on its `Delivery` row (the order carries no money field and there is no order-total or fulfil-to-sale path). A fee with more than two decimals is refused, not rounded (server rule).

**Permission truths.** `SupplierBillViewSet` reads with `IsInventoryRole` (Stock Manager, Store Manager, Admin; cashier and CPMS refused). `SupplierPaymentViewSet` reads with `IsInventoryRole` and creates with `IsManagerRole` (Store Manager/Admin only) — the stocker sees the money, a manager moves it. `DeliveryReadWritePermission` reads with the sales reader roles and writes with `DELIVERY_UPDATER_ROLES` (Store Manager, Admin, Stock Manager); on top of that `OwnSalesScopeMixin` scopes `Delivery.created_by`, so a cashier-only user reads **only their own** slips and another till's slip is a **404**, while the three store-wide roles keep the schedule. `StorageLocationViewSet` reads with `IsAuthenticated` and writes with `IsAdminRole` — narrower than the catalog's `IsInventoryRole` on purpose — and an Admin additionally sees deactivated places, which everyone else cannot see or assign.

**Stock truths.** Phase 5 adds no stock-per-location logic: `StorageLocation` is a **label** (`Product.stored_at`, default Store) with no quantity, transfer or batch effect, and no location stock counts or transfers exist. Packages change only how a quantity is *counted* (unit × factor); FIFO, batches and whole-unit refusals behave as in Phase 1d. inventory 0011 seeds **Store** and **Bodega** idempotently and case-insensitively (`Upper(name)` unique) and backfills every product, so no product is left without a shelf; `is_active: false` keeps labelling products that already point at a place, refuses new assignments (`INVALID_STORAGE_LOCATION`), and has no DELETE because the FK is PROTECT.

**Owner decision 2026-11-12 — create-only sales-order entry.** F3's *sales-order* Deliver toggle now has a surface: the Store Manager sales-orders page has a **New sales order** button that opens `sales/widgets/sales_order_form_dialog.dart`. The form takes a named customer (walk-in excluded), lines of active catalogue products only (an archived product or variant is hidden, as at the till), a unit menu reading “Product · UNIT (Name)”, a whole-unit pre-check from the server's `uom_is_whole`, an editable unit price defaulted from the catalogue price (owner-confirmed at closure), and an optional Deliver section (address, contact name and phone, scheduled date defaulting to tomorrow, fee ≥ 0 at two decimals). It posts `POST /api/v1/sales-orders/` with **no** `status` — the server writes the order as `CONFIRMED` — and the order and its delivery are created atomically. That is the whole of it: **no edit, delete, status change or fulfil-to-sale UI**, and the View sheet stays read-only; quotations still have no create UI. `SalesReadPOSWrite` lets a Cashier, Store Manager or Admin write and a Stock Manager only read (POST 403); the button lives only in the Store Manager sales shell. **Phase 6 B1 later closed the gap Phase 5 recorded here:** the server now refuses an order or quotation line naming an archived selling unit with 400 `INACTIVE_SELLING_UNIT`, and order `PUT`/`PATCH`/`DELETE` are 405 — see the Phase 6 section below.

### Phase 6 — cleanup: writes that obey their own contract (In Progress — QA complete, owner closure pending, decision 22)

**Guarded sales-order and quotation writes (B1, item 16 — the High one).** A sales order is **create-only** until Phase 7 ships the lifecycle actions: `SalesOrderViewSet.http_method_names = ("get", "head", "options", "post")`, so `PUT`/`PATCH`/`DELETE` answer **405 for every role, Admin included**, and an order carrying a `Delivery` (a `PROTECT`ed FK) can no longer surface a `ProtectedError` **500** — the same precedent `SalesTransactionViewSet` set. `POST` writes the order, its lines, its optional delivery and **one** `CREATE` audit row (order number, customer, line count, delivery yes/no) in **one** atomic block, so a refused create (an invalid delivery fee is refused after the order row exists) leaves no trail claiming an order that was never written. A quotation's `status` joins `quotation_no`/`created_by` as read-only, a PATCH carrying only a status changes nothing and writes no audit row, while a real `UPDATE`/`DELETE` is **Store Manager/Admin only** (`IsManagerRole`; a cashier gets 403) and carries its `UPDATE`/`DELETE` audit row in the **same transaction** as the write. A nested `items` write on update is refused **400** `{items: […]}` in `QuotationSerializer.validate`, before `create()` — DRF's model serializer cannot nest a writable `items` into an update and would otherwise raise an `AssertionError` **500**.

**Archived catalogue rows are refused at the boundary (B3, item 14).** `refuse_inactive_selling_unit` in `common/exceptions.py` (beside `refuse_fractional_whole_unit`, same reason for living in `common/`: both directions of the dependency graph ask it) raises `InactiveSellingUnit` → **400 `INACTIVE_SELLING_UNIT`** when the unit's variant **or** its product is archived. It is wired into `QuotationItemSerializer.validate` and `SalesOrderItemSerializer.validate`, and it runs **before the first write**, so a refused create leaves no document, no line, no delivery and no audit row — and, because number minting happens in `model.save`, it consumes **no** document number. The till keeps its own `InvalidSale` wording in `_validated_sale_lines`, but both read the same `is_active` flags.

**Race-safe document numbers (B4, item 19).** `common/numbering.generate_document_number` no longer reads the newest document and adds one (two creates read `-0007`, both write `-0008`, the loser dies on the unique field as a **500**). It reserves from the existing `DocumentCounter` row under `select_for_update` — the pattern `pos.services.next_number` already used for TRX/OR — seeded from `highest_existing_sequence` (now public) so a live document's number is never handed out twice. Callers are unchanged (quotations, orders, deliveries, requisitions), **no table and no migration** were added, and the reservation sits in a nested atomic: an outer rollback reclaims it, so the worst case is a gap, never a duplicate. A two-real-thread test with a barrier proves two concurrent quotation saves get distinct numbers.

**Money and state Minors (B2, B5).** `discount_share` now caps `cumulative = min(cumulative, header_discount)` and keeps its per-slice clamp, so an **over-receipt** can never allocate more discount than the PO header holds (bills still sum to the header exactly, e.g. 33.33/33.34/33.33), and the docstring example matches the arithmetic. `_money_round` became the public `money_round` (requisitions imports the public name; no private alias, no leftovers), `apps/users/views.py` catches `serializers.ValidationError` only — an unexpected error is now an honest **500**, not a fake 400 — and `StoreSettingsView.patch` returns **200 with no save and no `SETTINGS_UPDATE` row** when the body repeats the stored values (a save would bump `updated_at`, and `"12"` vs a stored `12.00` counts as unchanged). The purchase-order item serializer docstrings were aligned with the real `INVALID_PO` / null-unit behaviour.

**Seed repair (B6, item 17).** `seed_demo` keyed variants by the bare `variant_name`, so the two "Standard" variants collided and a half-built packaging shape (product exists, units/prices missing) could never repair. Variants are now keyed by **(product, variant name)**, the packaging guard checks the complete shape (product, both units, prices) and creates only the missing parts idempotently, and the stock gate is "the variant has any batch" — re-running the seed no longer raises `DoesNotExist` or duplicates a PO/receipt/batch. Wrong-but-present factors or prices are **not** corrected (recorded Minor, not a fix).

**Flutter Minors (F1, F2).** The till's low-stock badge is no longer a hardcoded 10: `0 < base stock < variant.minStockThreshold` is computed from the server threshold and carried through `PosCatalogItem` (threshold 0 or a disabled threshold → no badge; the catalogue helper's `<=` is deliberately not reused), and `PosCatalogItem` gained the flag the viewmodel was missing. The receipt test now feeds a **server** `change_given` that differs from paid − total, so the printed change comes from the server. One shared `core/format/money_input.dart` validator replaces the two duplicated dialog copies, money error fields use `errorMaxLines: 4` with a real **760 px / 1.3 ×** `didExceedMaxLines` regression, and **“New sales order” is hidden when the page failed to load** — the single golden capture this phase changed. Back office: a null VAT rate reads **“Not recorded”**, never an invented 0 % or ₱0.00 (the PO details crash is gone); a legacy product with a null `storedAtId` can finally take a location via explicit-touch tracking that still sends no `stored_at` when untouched; and a double-tapped “add location” returns a distinct "already adding" result instead of a false "added".

**Retained Minors / gotchas (recorded, not fixed here).** The `common/numbering.py` docstring still says the reservation "commits independently of the caller's insert" (with a nested atomic an outer rollback reclaims it — safe, wording only); the quotation nested-`items` 400 copy tells the clerk to "Void this quotation", an action the product does not have yet (status is read-only, no void route); the archived refusal's detail names the variant even when only the product is archived; the seed prints "Packaging repaired …" then "Packaging already seeded - skipping" on one run; B4's concurrency test covers quotations only (the helper is shared); the Flutter order form has no dedicated message for `INACTIVE_SELLING_UNIT` (the client filters active catalogue rows, the server refuses). **Baseline diagnostics, not introduced here** (review Minor #5, no fix in this close-out): untouched `apps/pos/tests_exception_extra.py` reports **12** pyright errors in the CLI baseline and the LSP+runner sweep but **0** from an earlier LSP-only probe — tool-dependent baseline noise, not a reproducible failure or a clean verdict — and untouched `apps/collectibles/models.py:138` reports 1 warning; `apps/inventory/tests_supplier_payables.py:496` does sit in B2's diff and carries 2 typing warnings on `with transaction.atomic()`, not a behavioural regression.
