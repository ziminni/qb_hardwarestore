Container architecture

Two processes, one database. The API owns all business logic and is the trust boundary: server prices, selling-unit conversion, payload validation, locked document numbering, idempotent checkout (P1); Admin-group authority + cashier scoping (P2); shift-gated debt-first returns (P3); persisted catalog + append-only records (P4); Store Manager user-write + manager unlinked returns (P5); POS evolution: CPMS Service fenced to /api/v1/integration/cpms/ (403 CPMS_SCOPE elsewhere). Phase 1b: pushed contents stay read-only; store Accept/Decline precedes accepted-line-only partial release and project-tagged utang. Phase 1d: the server decides what a whole unit is (UnitOfMeasure.is_whole), every database gets the twelve standard units, an unused selling unit can be removed, and a fractional quantity on a whole-count unit is refused on every path that carries one. Phase 4 (front counter, decision 18): shelf prices are VAT-inclusive and the server splits vatable_sales/vat_amount from the net at a per-sale vat_rate (returns use the sale's rate; legacy null = 0%); an Admin-only StoreSettings singleton holds VAT on/rate and the discount cap; a cashier discount needs a reason and stays under the cap unless a Store Manager/Admin approves on the spot through a one-time 5-minute token (five failures lock the pair, 429); split tenders record a server change_given from cash only and a non-cash overpay is refused 400; customer cheques stay PENDING and never reduce debt until a manager clears them; accounts carry several roles with an area picker and header switcher. Phase 5 (back office, decision 18), owner-closed: a PO line names its variant_uom, so packages are ordered and received in that unit while stock enters in base units (qty × factor, landed cost per base = unit cost ÷ factor; an unrepresentable base quantity is refused 400 RECEIPT_QUANTITY_UNREPRESENTABLE); processing a goods receipt writes one immutable SupplierBill (received value less its cent-exact discount share, PO VAT snapshot, receipt date + supplier terms) with locked, audited partial SupplierPayments (Store Manager/Admin pay, Stock Manager reads); a Delivery slip hangs off a sale or a sales order and moves forward only (SCHEDULED → OUT_FOR_DELIVERY → DELIVERED / FAILED + reason), its fee charged on top of the goods net and never discounted; StorageLocation (seeded Store, Bodega) is an Admin-managed label behind Product.stored_at — a label, not a stock ledger. Contract v0.3 is owner-provisionally accepted (2026-11-11); v0.2 closed 2026-11-08 with accepted QA limits. Data screens use API responses; store contact constants and access banners remain static, while VAT and discount settings are API-backed.

Phase 1b lifecycle — implementation, not deployment

CPMS import → WAITING → store ACCEPTED (every line true/false, at least one true) or whole DECLINED (reason required). Null intent means unanswered, not false. Strict booleans/reasons, no quantity/price/status edits. Accept reserves no stock and books no money. Only accepted lines release; PARTIAL keeps token live, eligible-line completion RELEASED spends it. DECLINED/CLOSED also spend it; typed WAITING/DECLINED scan refusals precede token-used checks. All transitions share token→request locks and fresh state.

Expected amount is known persisted released sale value + current-price true-line outstanding (outstanding sum HALF_UP once), independent of debt/payments. Unknown historical baseline stays null. CLOSED after acceptance retains abandoned shortfall in budget; before review stays null. CPMS read-back adds intent/reasons/budget, no unit prices, stock or token. Phase 1d — the unit decides, not the client

UnitOfMeasure.is_whole is the one source of truth for "counted in ones". Migration 0008 adds the column and seeds 12 standard units in every database: PC BAG BOX PACK ROLL SHEET whole, KG G M CM L ML measured. Lookups are case-insensitive because codes are unique only case-sensitively, an existing row is flagged rather than recased, and RL is accepted as the Roll row so no second Roll is created. The reverse is deliberately a noop: deleting those rows would delete units that selling units and past lines may point at.

The client no longer ships a code list. lib/core/units/whole_units.dart is deleted; the till reads uom_is_whole off the selling unit and the details dialog prints Whole or Measured in words, not colour alone.

One refusal, one code: common/exceptions.py WholeUnitQuantity (400 WHOLE_UNIT_QUANTITY, detail naming line, product and unit) behind the shared refuse_fractional_whole_unit. It lives in common/ because the rule spans both directions of the app dependency graph: the POS validator, the quotation/sales-order/purchase-order serializers, the goods-receipt view, the stock-adjustment serializer and the CPMS import all ask it, and none may import another app's API module to do so. Every raise site checks before the first write, so the 400 also means nothing changed. Paths: sale, held-cart complete, return, release, quotation, sales order, purchase order, goods receipt, stock adjustment, CPMS import.

DELETE /api/v1/variant-uoms/{id}/ removes an unused extra selling unit. 400 BASE_UNIT_REQUIRED for the factor-1 unit. 400 SELLING_UNIT_IN_USE when any of the five PROTECT tables references it (sale line, held cart, project request, quotation, sales order). 404 for a bad id and for a second delete of the same row, never a 500. Price and code stay editable either way; the audit row is written inside the same transaction, so a success is 204 plus one DELETE row and a refusal writes nothing.

Removal and the writers share a lock. apps/inventory/services.py lock_selling_units / lock_selling_unit_lines take select_for_update() in sorted PK order over the units a write is about to reference; removal takes the same row lock. Two writers queue in one order instead of deadlocking, and a unit that vanished between read and lock becomes 400 SELLING_UNIT_IN_USE naming the line rather than a foreign-key 500.

Phase 4 — front counter: VAT, discount, split + cheque, pager, labels, areas

Settings. StoreSettings is a database-enforced singleton (pk=1 check constraint): vat_registered (default true), vat_rate 12.00, discount_cap_percent 10.00. One GET/PATCH path — read by any signed-in user, written by Admin only and audited. The Admin Settings page edits it through the app-scoped StoreSettingsViewmodel; store name/email/phone stay inline constants.

VAT. Shelf prices INCLUDE VAT, so vat_split works backwards from the net: vatable = net / (1 + rate/100), vat = net − vatable, ROUND_HALF_UP once; a non-VAT store gets 0/0 plus a flag. Each sale stores its own vat_rate (pos 0013) so a linked return refunds under the rate the sale was written at — legacy rows hold null and read as 0% rather than today's rate, and an unlinked return has no original to read and uses today's settings.

Discount. Optional discount {kind, value, reason} on checkout and held-cart complete; percent is of gross, a reason is required above zero and it can never exceed gross. Above the cap the sale needs a discount_approval token from POST /api/v1/discount-approvals/: Store Manager/Admin credentials are checked server-side and never stored, the token is a signature over a DiscountApproval row bound to the percent, valid 5 minutes, and spent under a row lock by one sale, so a replay cannot discount twice. A cashier cannot approve themselves. The endpoint shares apps.users.lockout: five failures per (username, address) answer 429 DISCOUNT_APPROVAL_LOCKED and each failure is audited without the password. Returns refund each line's net share; the reports show Discounts and VAT again.

Split tenders and change. payments[] may mix cash, GCash and cheque. The server computes change_given (pos 0014) as money in hand above the net, capped at the cash tendered; a non-cash overpay is refused 400 PAYMENT_EXCEEDS_TOTAL instead of silently swallowing it. The Z-reading subtracts that change from cash_sales, which fixes a pre-existing drawer overstatement QA found on any cash overpay, and the receipt prints the server's change rather than recomputing it.

Cheques. No new model: a cheque is a Payment row with method=CHEQUE, cheque_number/bank/cheque_date and a status of PENDING/CLEARED/BOUNCED (other methods are CLEARED; pos 0012 backfills old rows). A cheque needs a named customer (CHEQUE_NEEDS_CUSTOMER), because there is nobody to owe the money. A pending cheque is NOT paid: its amount posts to the customer's utang ledger through Payment.ledger and only POST /api/v1/cheques/{id}/clear/ applies a ledger payment, while bounce/ with a reason leaves it owed. Store Manager/Admin only, once-only 409 CHEQUE_ALREADY_DECIDED, locked and audited. Utang payments offer the same cheque option (collectibles 0003 shares the method choice). Refunds never pay out by cheque.

Several roles. The user serializer returns roles[] (recognized staff areas, deduplicated in stable order; CPMS/ad-hoc groups excluded) beside legacy role; admin writes send roles[] as a full replacement, with USER_ADMIN_FORBIDDEN/LAST_ADMIN applying to every role added or removed and CPMS Service never combinable with staff roles. One area signs straight in; several land on /select-area (AreaPickerPage, the 41st route); the header AreaSwitcherMenu changes area; redirectFor honours a stored choice only while the server still assigns it (per device, active_area_store.dart).

Pager and labels. DataPanel pages client-side at 25 rows ("1 to 25 of N", hidden at 25 or fewer, paginate: false opt-out, reset on filter). Products gains a Barcode list export (features/labels/barcode_list_{document,csv,dialog}.dart): an A4 PDF with EAN only when the check digit is valid and Code 128 otherwise, plus a CSV with a BOM and a ' prefix on cells starting = + - @, tab or CR, so a product name cannot execute in a spreadsheet.

Phase 5 — back office: packages, payables, delivery, bodega (owner-closed)

Order by package (B1/F1, inventory 0009). POItem.variant_uom names the unit the line is written in; the migration backfills every existing line to its variant's base unit, so an old line keeps meaning factor 1. ordered_qty/unit_cost are in that unit and the whole-unit rule is that unit's. Receiving counts in the line's unit and the batch is written qty = received × factor at unit_cost ÷ factor. A conversion not exactly representable in two-decimal base stock is refused 400 RECEIPT_QUANTITY_UNREPRESENTABLE before any write, and a referenced unit is frozen (identity + factor) under the Phase 1d sorted-PK deletion locks, so changing a factor never re-measures existing orders.

Supplier payables (B2, inventory 0010). Processing a goods receipt writes exactly one SupplierBill in the same transaction — the receipt's package qty × package cost, less that receipt's cumulative cent-exact share of the PO discount, with the PO's VAT snapshot and due_date = receipt date + Supplier.terms_days (default 0 = on receipt). A receipt with zero gross value makes no bill, and pre-B2 receipts get no retroactive bill. Bills are immutable: no POST/PATCH/DELETE for any role, Admin included. A SupplierPayment (cash / cheque / bank transfer, optional reference, cheque no./bank/date, partial allowed, never above the balance) moves the balance under a row lock and is audited in the same transaction; refusals are 400 OVERPAYMENT and BILL_PAID. GET /suppliers/payables/ answers original/paid/balance/overdue per supplier. The PO header's discount_amount and vat_inclusive (default true, rate from store settings) reach the bill, never the batch landed cost.

Delivery (B3, pos 0015, users 0005). A Delivery hangs off exactly one sale or one sales order (model check constraint) and is created inside that document's own atomic block — so there is no standalone POST /deliveries/ (405 for every role) and a refused sale leaves no slip. start (SCHEDULED → OUT_FOR_DELIVERY), deliver (→ DELIVERED, terminal) and fail (→ FAILED, required reason) move forward only, under a row lock with a re-read: a stale move is 409 and each move writes one audit row.

Financial truths (in process_sale / process_return). The delivery charge is charged on top of the goods net and is never discounted — gross and the discount cap are computed from the lines only, grand_total = goods_net + delivery_fee — and the VAT split is taken from that grand total, so the receipt adds up to what the customer actually pays. The fee is stored on the sale (delivery_fee) as well as on the slip, because the receipt, Z-reading and change arithmetic read the sale. Owner-confirmed 2026-11-12: the discount cap and the return's net-refund share exclude the delivery fee (sale_net = grand_total − delivery_fee), a delivery fee is not refunded, a zero fee is allowed, and a sales-order delivery fee lives only on its Delivery row (the order carries no money field and there is no order-total or fulfil-to-sale path). A fee with more than two decimals is refused, not rounded (server rule).

Permission truths. Bills read with IsInventoryRole (Stock Manager, Store Manager, Admin; cashier and CPMS refused); payments read with it and create with IsManagerRole (Store Manager/Admin). Deliveries read with the sales reader roles and write with DELIVERY_UPDATER_ROLES (Store Manager, Admin, Stock Manager); OwnSalesScopeMixin additionally scopes Delivery.created_by, so a cashier-only user reads only their own slips and another till's slip is a 404, while the three store-wide roles keep the schedule. Storage locations read with IsAuthenticated and write with IsAdminRole (narrower than the catalog's IsInventoryRole on purpose); an Admin also sees deactivated places.

Stock truths. No stock-per-location logic: StorageLocation is a label (Product.stored_at, default Store) with no quantity, transfer or batch effect, and no location counts or transfers exist. inventory 0011 seeds Store and Bodega idempotently and case-insensitively (Upper(name) unique) and backfills every product; is_active: false keeps labelling products that already point at a place, refuses new assignments (INVALID_STORAGE_LOCATION), and there is no DELETE because the FK is PROTECT.

Phase 6 — cleanup: writes that obey their own contract (In Progress — QA complete, owner closure pending, decision 22)

Guarded sales-order and quotation writes (B1, item 16 — the High one). A sales order is create-only until Phase 7 ships the lifecycle actions: SalesOrderViewSet.http_method_names = ("get", "head", "options", "post"), so PUT/PATCH/DELETE answer 405 for every role, Admin included, and an order carrying a Delivery (a PROTECTed FK) can no longer surface a ProtectedError 500 — the same precedent SalesTransactionViewSet set. POST writes the order, its lines, its optional delivery and one CREATE audit row (order number, customer, line count, delivery yes/no) in one atomic block, so a refused create (an invalid delivery fee is refused after the order row exists) claims nothing that was never written. A quotation's status joins quotation_no/created_by as read-only; a PATCH carrying only a status changes nothing and writes no audit row, a real UPDATE/DELETE is Store Manager/Admin only (IsManagerRole; a cashier gets 403) and carries its audit row in the same transaction, and a nested items write on update is refused 400 in QuotationSerializer.validate — before DRF's model serializer would trip an AssertionError 500.

Archived catalogue rows are refused at the boundary (B3, item 14). refuse_inactive_selling_unit in common/exceptions.py (beside refuse_fractional_whole_unit, same reason for living in common/: both directions of the dependency graph ask it) raises InactiveSellingUnit → 400 INACTIVE_SELLING_UNIT when the unit's variant or its product is archived. It is wired into both item serializers and runs before the first write, so a refused create leaves no document, line, delivery or audit row — and, because number minting happens in model.save, it consumes no document number.

Race-safe document numbers (B4, item 19). common/numbering.generate_document_number no longer reads the newest document and adds one (two creates read -0007, both write -0008, the loser dies on the unique field as a 500).
