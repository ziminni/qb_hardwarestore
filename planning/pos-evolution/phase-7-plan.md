## Binding rules

- **RED-first proof per task:** each behaviour lands with a test witnessed failing without it (output recorded in the task line), then GREEN.
- **Server is the trust boundary:** status, prices, remaining quantities, roles and stock live in Django. Status is never client-writable; every transition is a server action under a `select_for_update` lock on the order row, atomic with its audit row.
- **Orchestration:** backend sequential (B1 → B5); at most **2 Flutter lanes** on disjoint files (F1 sales side, F2 till side). Controller owns full suites and goldens.
- **Databases:** never start/migrate/reset/restart dev (entrypoint auto-migrates). Tests and QA on isolated `buildpro_p1d_qa_*` only.
- **Migrations (assuming Phase 6 added none; if it did, shift each by one and update this list before dispatch):**
  - pos **`0016_sales_order_lifecycle`** (B1): `SalesOrder.Status` gains `PARTIAL`, `CANCELLED` (legacy `PROCESSING`/`READY` stay as choices, never written); `SalesOrder.cancel_reason`, `cancelled_by`, `cancelled_at`; `SalesOrderItem.fulfilled_qty` (default 0) and `cancelled_qty` (default 0); `SalesItem.order_line` (FK `SalesOrderItem`, nullable, PROTECT); `DiscountApproval.sales_order` (FK, nullable, PROTECT); `Delivery` constraint `delivery_exactly_one_document` (`apps/pos/models.py:742-749`) replaced by "at least one document" so a re-linked delivery keeps its order. No data rewrite of legacy rows.
  - users **`0006_sales_order_audit`** (B1): `AuditLog.ActionType.SALES_ORDER` (one type for create/edit/cancel/fulfil, like `DELIVERY` at `apps/users/models.py:174-178`).
- **Tags:** 🤖 agent-built, controller-reviewed. 🤝 owner reviews/writes with the agent.

## Goal

Orders become real work: managers edit or cancel them with a reason, cashiers fulfil them at the till into ordinary sales (partially or fully) at the agreed price, with stock, VAT, payments and the delivery fee handled exactly as at checkout.

## Execution checklist

- [ ] **B1 — 🤖 Schema + status machine.** Migrations above. One transition table as data (like `DELIVERY_TRANSITIONS`, `services.py:103`): CONFIRMED → PARTIAL → COMPLETED; CONFIRMED → CANCELLED; PARTIAL → COMPLETED (remainder cancelled). Legacy PROCESSING/READY are **read as CONFIRMED** on the wire and by every rule (`effective_status`); no code path writes them. Order serializer exposes read-only per-line `fulfilled_qty`, `cancelled_qty`, `remaining_qty`. RED: legacy READY order reads as CONFIRMED; a direct status write is ignored/405.
- [ ] **B2 — 🤝 Price guard at order save (create and edit).** Per line, catalogue price = `variant_uom.default_selling_price`; a line below it is a discount of `(catalogue − agreed) / catalogue`. The **largest line percent** is compared to `StoreSettings.discount_cap_percent`: within cap → saved; above cap and no token → 400 `DISCOUNT_OVER_CAP` (+ `cap_percent`/`requested_percent`); token present → `_consume_approval(token, percent_needed=…)` (reused, not copied), stamped `used_at` + `sales_order` in the save transaction; bad token → `DISCOUNT_APPROVAL_INVALID`. Above-catalogue prices are allowed. Same rule for every role (a manager mints a token with their own credentials). Refusal writes nothing. RED: an order at 50% below catalogue saves today.
- [ ] **B3 — 🤖 Edit and cancel (managers).** `PATCH /sales-orders/{id}/` re-enabled for Store Manager/Admin only (`IsManagerRole`), only while `effective_status == CONFIRMED` and nothing fulfilled: lines, notes and delivery fields (address/contact/date/fee while the delivery is SCHEDULED); `reason` required; re-runs B2; audited `SALES_ORDER` with before/after summary. `POST /sales-orders/{id}/cancel/ {reason}`: CONFIRMED → CANCELLED; PARTIAL → COMPLETED with remaining moved to `cancelled_qty`. Delegated default (owner may override): cancelling an unfulfilled order moves a SCHEDULED delivery to FAILED with reason "Order cancelled: …"; refused if the delivery is OUT_FOR_DELIVERY/DELIVERED. DELETE stays 405 (Phase 6). Cashier edit/cancel → 403. RED: each refusal/transition.
- [ ] **B4 — 🤝 Fulfilment entry through `process_sale`.** `POST /sales-orders/{id}/fulfil/ {lines:[{order_line, qty}], payments, delivery?}` with `Idempotency-Key`, POS role. Order row locked; `qty ≤ remaining`, whole-unit rule, archived-unit refusal (Phase 6 B3). Calls `process_sale` with a new `order_lines` input so **all checkout guards run unchanged**: open shift, unit locks, FIFO in base units (`InsufficientStock` refuses the whole fulfilment), VAT split, split/cheque/utang payments, credit limit, change, OR, low-stock check, idempotency replay. Only the price source differs: each `SalesItem.unit_price` = order line price, `order_line` set; no sale-level discount (the approval was spent at save); customer = order customer. **Delivery fee on the first fulfilment only:** the existing `Delivery` row gets `sale` set (keeps `sales_order`), `txn.delivery_fee` = its fee, inside `grand_total`; later fulfilments carry no fee and refuse a `delivery` payload. Then `fulfilled_qty += qty`, status PARTIAL or COMPLETED, audit `SALES_ORDER` + the normal `SALE` row, all in one transaction. Fulfilling a CANCELLED/COMPLETED order → 400. RED: double fulfilment race (two locks, one wins), over-remaining qty, no shift, short stock, replayed key, fee charged twice.
- [ ] **B5 — 🤖 Stock hint, returns and contract.** Order read adds per-line `available_qty` (sellable stock in that line's unit, read-only; no reservation). Returns of a fulfilment sale use existing rules (`_return_unit_price` reads the sold line price, `services.py:1381-1407`) and do **not** change `fulfilled_qty` or reopen the order; test pins it. `ENDPOINTS.md`: sales-orders rows (PATCH/cancel/fulfil, roles, codes), lifecycle and fee note; the "no fulfil-to-sale path" comments at `models.py:681` and `serializers.py:437` corrected.
- [ ] **F1 — 🤖 Order lifecycle UI (sales side).** Enum adds `partial`, `cancelled`; `processing`/`ready` from the wire map to `confirmed`. Order sheet shows ordered / fulfilled / remaining and the per-line stock hint ("enough" / "short by N"). Managers see **Edit** (form in edit mode; on `DISCOUNT_OVER_CAP` opens `PosDiscountApprovalDialog`, then resubmits with the token) and **Cancel** (reason required); cashiers and Stock Manager see neither. Server refusals shown inline, input kept. Supersede `sales_read_only_actions_test.dart:238-276` for orders only (Edit/Cancel for managers, still no Delete); the quotations pin (`:214-236`) is unchanged.
- [ ] **F2 — 🤖 Till "Open order" flow.** POS action lists CONFIRMED/PARTIAL orders; choosing one loads remaining lines like a resumed held cart, qty editable down to 0 and capped at remaining, prices read-only from the order, per-line stock hint. Payment dialog reused: fee shown (not editable) on the first fulfilment, delivery toggle hidden; submits to `fulfil/` with an idempotency key; receipt as for any sale. Refusal codes (`NO_OPEN_SHIFT`, `INSUFFICIENT_STOCK`, over-remaining) shown with the cart kept.
